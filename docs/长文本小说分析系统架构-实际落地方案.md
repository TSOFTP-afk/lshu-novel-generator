## 一、落地总原则

### 1.1 先保护现有能力

灵枢当前已经有可用的全书三级分析流程、人物/世界观写回、章节事件写回、Truth File、RAG 和多 Agent 审查。下一代分析系统第一阶段必须遵守：

- 不删除现有 `_analyze_book_in_batches` 能力。
- 不删除现有 `_apply_book_analysis_result`，但改变其调用入口。
- 不让“AI 分析全书”默认覆盖正式人物卡、世界观和章节事件。
- 新增功能默认走草案层，用户确认后才写回。
- 所有新增表必须兼容旧数据库，无需用户手工迁移。

### 1.2 先做最小闭环

第一阶段只做最有价值、风险最小的闭环：

```text
现有全书三级分析
  -> 生成分析草案 analysis_cards
  -> 生成 diff_json
  -> UI 展示草案和差异
  -> 用户确认
  -> 调用现有写回逻辑
  -> 记录审计日志
```

暂时不在第一阶段实现完整实体共指、别名演化图、假设性回溯和外部向量库。

### 1.3 保持双轨运行

短期内保留两条路径：

| 路径 | 用途 | 默认状态 |
|------|------|----------|
| 旧路径：分析后直接写回 | 兼容已有能力、调试兜底 | 隐藏或作为高级选项 |
| 新路径：分析后生成草案 | 正式用户路径 | 默认启用 |

推荐加一个内部开关：

```python
BOOK_ANALYSIS_DRAFT_MODE = True
```

或者复用设置项，允许用户在调试时回退旧路径。

## 三、第一阶段 MVP 范围

### 3.1 MVP 要解决的问题

MVP 只解决当前最危险的问题：全书分析结果会直接覆盖正式数据。

MVP 完成后，用户流程变为：

```text
点击“AI 分析全书”
  -> 后台运行现有三级分析
  -> 结果写入 analysis_runs / analysis_cards
  -> 右侧打开“分析”Tab
  -> 用户查看书籍、人物、世界观、章节事件草案
  -> 用户点击“应用”
  -> 系统创建快照/审计日志
  -> 调用现有写回逻辑写入正式数据
```

### 3.2 MVP 不解决的问题

以下内容暂不进入第一阶段：

- 完整实体共指消解。
- `analysis_entities` / `analysis_mentions` 的完整生产流程。
- ARS 精准计算。
- 块级 RAG 索引。
- 单章修改后的自动局部重算。
- 复杂差异合并 UI。

第一阶段可以先把一整个全书分析结果视为一张或多张草案卡：

| 草案卡 | 内容来源 |
|--------|----------|
| `book_summary` | `book_outline`、`book_outline_form` |
| `world` | `world_form`、`world_entries`、`world_text` |
| `characters` | `characters` 数组 |
| `chapters` | `chapter_updates` |
| `unresolved` | `analysis_unresolved` |

### 3.3 MVP 验收标准

- 全书分析完成后不再自动修改 `characters`、`books.world_data_json`、`chapter_events`。
- 分析结果能在重启后继续查看。
- 用户点击“应用草案”后，才执行现有正式写回。
- 应用前后写入 `analysis_audit_logs`。
- 旧的直接写回路径可作为内部兜底，但默认不可触发。

## 四、数据库落地方案

### 4.1 P0 必须新增的表

P0 先新增四张表：

1. `analysis_runs`
2. `analysis_cards`
3. `analysis_audit_logs`
4. `analysis_apply_snapshots`

`analysis_blocks` 可以 P1 再接入。P0 如果暂时沿用现有三级分析结果，不强依赖分块持久化。

### 4.2 `analysis_runs`

```sql
CREATE TABLE IF NOT EXISTS analysis_runs (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    book_id INTEGER NOT NULL,
    scope_type TEXT NOT NULL DEFAULT 'book',
    status TEXT NOT NULL DEFAULT 'created',
    pipeline_version TEXT NOT NULL DEFAULT 'draft_mvp_v1',
    input_hash TEXT NOT NULL DEFAULT '',
    summary TEXT NOT NULL DEFAULT '',
    error_text TEXT NOT NULL DEFAULT '',
    meta_json TEXT NOT NULL DEFAULT '{}',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    completed_at DATETIME,
    FOREIGN KEY (book_id) REFERENCES books(id) ON DELETE CASCADE
);
```

### 4.3 `analysis_cards`

```sql
CREATE TABLE IF NOT EXISTS analysis_cards (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    book_id INTEGER NOT NULL,
    run_id INTEGER NOT NULL,
    card_uid TEXT NOT NULL,
    card_type TEXT NOT NULL,
    entity_uid TEXT NOT NULL DEFAULT '',
    card_version INTEGER NOT NULL DEFAULT 1,
    ars_score REAL NOT NULL DEFAULT 0.0,
    status TEXT NOT NULL DEFAULT 'draft',
    payload_json TEXT NOT NULL,
    diff_json TEXT NOT NULL DEFAULT '{}',
    applied_table TEXT NOT NULL DEFAULT '',
    applied_id INTEGER,
    applied_at DATETIME,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (book_id) REFERENCES books(id) ON DELETE CASCADE,
    FOREIGN KEY (run_id) REFERENCES analysis_runs(id) ON DELETE CASCADE,
    UNIQUE(run_id, card_uid)
);
```

### 4.4 `analysis_audit_logs`

```sql
CREATE TABLE IF NOT EXISTS analysis_audit_logs (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    book_id INTEGER NOT NULL,
    run_id INTEGER,
    card_id INTEGER,
    action TEXT NOT NULL,
    target_type TEXT NOT NULL,
    target_uid TEXT NOT NULL DEFAULT '',
    old_value_json TEXT NOT NULL DEFAULT '{}',
    new_value_json TEXT NOT NULL DEFAULT '{}',
    reason TEXT NOT NULL DEFAULT '',
    confidence REAL NOT NULL DEFAULT 0.0,
    actor TEXT NOT NULL DEFAULT 'system',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (book_id) REFERENCES books(id) ON DELETE CASCADE,
    FOREIGN KEY (run_id) REFERENCES analysis_runs(id) ON DELETE SET NULL,
    FOREIGN KEY (card_id) REFERENCES analysis_cards(id) ON DELETE SET NULL
);
```

### 4.5 `analysis_apply_snapshots`

`chapter_snapshots` 只能覆盖章节正文/大纲，无法覆盖书籍大纲、世界观、人物卡和关系。因此需要一个分析写回快照表。

```sql
CREATE TABLE IF NOT EXISTS analysis_apply_snapshots (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    book_id INTEGER NOT NULL,
    run_id INTEGER,
    label TEXT NOT NULL,
    snapshot_json TEXT NOT NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (book_id) REFERENCES books(id) ON DELETE CASCADE,
    FOREIGN KEY (run_id) REFERENCES analysis_runs(id) ON DELETE SET NULL
);
```

快照内容建议包含：

```json
{
  "book": {"outline_text": "...", "outline_data_json": "...", "world_data_json": "..."},
  "characters": [{ "id": 1, "name": "...", "role": "...", "profile_data_json": "..." }],
  "relationships": [{ "id": 1, "source_character_id": 1, "target_character_id": 2 }],
  "world_entries": [{ "id": 1, "name": "...", "content_text": "..." }],
  "chapter_events": [{ "id": 1, "chapter_id": 1, "label": "..." }],
  "chapters": [{ "id": 1, "outline": "...", "summary_text": "..." }]
}
```

### 4.6 索引

```sql
CREATE INDEX IF NOT EXISTS idx_analysis_runs_book ON analysis_runs(book_id, created_at);
CREATE INDEX IF NOT EXISTS idx_analysis_runs_status ON analysis_runs(status, updated_at);
CREATE INDEX IF NOT EXISTS idx_analysis_cards_run ON analysis_cards(run_id, card_type, status);
CREATE INDEX IF NOT EXISTS idx_analysis_cards_book ON analysis_cards(book_id, card_type, updated_at);
CREATE INDEX IF NOT EXISTS idx_analysis_audit_logs_book ON analysis_audit_logs(book_id, created_at);
CREATE INDEX IF NOT EXISTS idx_analysis_apply_snapshots_book ON analysis_apply_snapshots(book_id, created_at);
```

### 4.7 Database 修改点

在 `Database.initialize()` 的建表脚本中加入上述表和索引。

短期新增方法：

```python
def create_analysis_run(self, book_id: int, scope_type: str = "book", meta: dict | None = None) -> int: ...
def update_analysis_run_status(self, run_id: int, status: str, *, summary: str = "", error_text: str = "", meta: dict | None = None) -> None: ...
def create_analysis_card(self, book_id: int, run_id: int, card_uid: str, card_type: str, payload: dict, diff: dict | None = None, status: str = "draft") -> int: ...
def list_analysis_runs(self, book_id: int, limit: int = 20) -> list[sqlite3.Row]: ...
def list_analysis_cards(self, run_id: int) -> list[sqlite3.Row]: ...
def get_analysis_card(self, card_id: int) -> sqlite3.Row | None: ...
def mark_analysis_card_applied(self, card_id: int, applied_table: str = "", applied_id: int | None = None) -> None: ...
def create_analysis_apply_snapshot(self, book_id: int, run_id: int | None, label: str, snapshot: dict) -> int: ...
def create_analysis_audit_log(...): ...
```

中期将这些方法迁移到 `AnalysisStore`，避免 `database.py` 继续膨胀。

## 五、新增 `novel_app/analysis` 包

### 5.1 `models.py`

定义轻量数据结构，避免 UI 和数据库层直接传复杂裸 dict。

```python
@dataclass(frozen=True)
class AnalysisCardDraft:
    card_uid: str
    card_type: str
    payload: dict[str, Any]
    diff: dict[str, Any]
    status: str = "draft"
    ars_score: float = 0.0
```

```python
@dataclass(frozen=True)
class AnalysisApplyResult:
    applied_cards: int
    skipped_cards: int
    snapshot_id: int | None
    audit_log_ids: list[int]
```

### 5.2 `store.py`

`AnalysisStore` 是对 `Database` 分析表方法的薄封装。

职责：

- 创建/更新 `analysis_runs`。

- 读取最近分析运行。

- AI 调用。
- UI 展示。
- 正式数据合并规则。

第一阶段核心文件。

职责：

- 将全书分析 payload 拆成多张草案卡。

建议函数：

```python
def split_book_analysis_payload(payload: dict[str, Any]) -> list[AnalysisCardDraft]: ...
def build_book_analysis_diff(database: Database, book_id: int, card: AnalysisCardDraft) -> dict[str, Any]: ...
```

## 六、全书分析接入改造

### 6.1 当前关键路径

当前路径是：

```text
_analyze_book_full
  -> _analyze_book_in_batches
  -> done(payload)
  -> _apply_book_analysis_result(book_id, payload)
```

需要改为：

```text
_analyze_book_full
  -> create_analysis_run
  -> _analyze_book_in_batches
  -> done(payload)
  -> save_book_analysis_draft(run_id, payload)
  -> _open_drawer("analysis")
  -> _refresh_analysis_tab()
```

### 6.2 `_analyze_book_full` 修改点

当前 `done(payload)` 中直接写回。

目标：

```python
def done(payload: Any) -> None:
    if not isinstance(payload, dict):
        return
    run_id = self.database.create_analysis_run(book_id, meta={...})
    card_ids = self._save_book_analysis_draft(book_id, run_id, payload)
    self.database.update_analysis_run_status(run_id, "awaiting_review", summary=f"生成 {len(card_ids)} 张分析草案")
    self._open_drawer("analysis")
    self._refresh_analysis_tab()
```

更稳妥的做法是在后台开始前创建 `run_id`，失败时能更新状态：

```text
created -> running -> awaiting_review / failed / cancelled
```

### 6.3 新增 `_save_book_analysis_draft`

建议先放在 `qt_app.py`，后续迁到 `analysis/pipeline.py`。

职责：

- 调用 `split_book_analysis_payload(payload)`。
- 为每张草案补 diff。
- 写入 `analysis_cards`。
- 写入一条 `analysis_audit_logs(action="draft_created")`。

### 6.4 `_apply_book_analysis_result` 改职责

保留函数主体，但重命名或包一层：

```python
def _apply_confirmed_book_analysis_result(self, book_id: int, payload: dict[str, Any], *, run_id: int | None = None) -> None:
    ...
```

或者保留原名，但增加注释和调用约束：

```python
def _apply_book_analysis_result(...):
    """Only call after user explicitly confirms an analysis draft."""
```

关键点：

- 不能再由 `_analyze_book_full.done` 直接调用。
- 应用前必须创建 `analysis_apply_snapshots`。
- 应用后必须标记卡片 `applied`。
- 应用后必须写审计日志。

### 6.5 旧路径兜底

可以保留一个隐藏调试方法：

```python
def _apply_book_analysis_result_legacy_direct(...)
```

或者设置项：

```python
if not self.book_analysis_draft_mode:
    self._apply_book_analysis_result(book_id, payload)
```

默认必须为草案模式。

## 七、UI 落地方案

### 7.1 第一阶段 UI 最小设计

新增右侧抽屉 Tab：`分析`。

最小控件：

- 分析运行列表。
- 当前运行的草案卡列表。
- 草案详情预览。
- 按钮：`应用选中`、`应用全部 stable/草案`、`拒绝选中`、`刷新`。

不需要第一阶段做复杂左右 diff 视图。可以先用文本摘要展示 diff。

### 7.2 `DRAWER_TAB_SEQUENCE`

当前：

```python
DRAWER_TAB_SEQUENCE = ("overview", "outline", "characters", "star", "world", "skills", "review", "tasks")
```

目标：

```python
DRAWER_TAB_SEQUENCE = ("overview", "outline", "characters", "star", "world", "skills", "analysis", "review", "tasks")
```

### 7.3 新增 `_build_analysis_tab`

建议结构：

```text
分析
├── 顶部状态：最近运行、状态、生成时间
├── 左侧/上方：草案卡列表
├── 中间：草案内容预览
├── 下方：差异摘要 + 操作按钮
```

方法建议：


## 十三、风险与回滚策略

### 13.1 风险：写回路径误触发

风险：

- 全书分析完成后仍误调用旧 `_apply_book_analysis_result`。

控制：

- 增加测试断言。
- `_apply_book_analysis_result` 增加注释和可选参数 `confirmed=True`。
- 未确认调用时抛错或写警告。

### 13.2 风险：分析草案无法应用

风险：

- 草案卡拆分后 payload 结构与旧写回函数不兼容。

控制：

- P0 草案卡保留原始完整 payload。
- “应用全部”时可直接将完整 payload 传给旧写回函数。
- 细粒度卡片应用后续再做。

### 13.3 风险：快照不完整

风险：

- 应用后用户想回滚，但快照缺字段。

控制：

- `analysis_apply_snapshots` 第一阶段保存全量相关正式数据。
- 不只依赖 `chapter_snapshots`。

### 13.4 风险：UI 复杂度扩大

风险：

- 新分析 Tab 过复杂，拖慢落地。

控制：

- 第一阶段只做列表 + 文本预览 + 应用按钮。
- 精细 diff、字段级勾选、颜色状态后续迭代。

### 13.5 回滚策略

如果 P0 上线后出现问题：

1. 保留新增表，不删除用户数据。
2. 将 `BOOK_ANALYSIS_DRAFT_MODE` 设为 `False` 可临时恢复旧路径。
3. 使用 `analysis_apply_snapshots` 手动恢复最近一次应用前状态。
4. 新分析 Tab 可隐藏，不影响写作、审查、RAG 和导出。

## 当前最优实施顺序

推荐立即按以下顺序开工：

1. 新增 `analysis_runs`、`analysis_cards`、`analysis_audit_logs`、`analysis_apply_snapshots`。
2. 新增 `AnalysisStore` 和基础测试。
3. 改 `_analyze_book_full.done`，让全书分析结果先保存草案。
4. 新增最小“分析”Tab，能看草案。
5. 增加“应用草案”按钮，确认后调用现有 `_apply_book_analysis_result`。
6. 应用前创建快照，应用后写审计日志。
7. 再做 `AnalysisChunker` 替换当前纯字符切片。

这条路线的好处是：第一阶段就能解决当前最大风险“AI 分析直接覆盖作者设定”，同时尽量复用已有成熟代码，避免一开始陷入实体共指和大规模架构重构。
